## 解析进度条（08:50）

需求：解析过程也要有进度条。

### 实现
解析原本是「一个请求干完所有事」，前端拿不到中途进度。做法：
- `app.py`：模块级 `_parse_state {seq, active, percent, stage}` + `threading.Lock`，`parse_progress_reset/parse_progress/parse_progress_finish` 三个函数；`api_parse` 里按阶段上报 12/26/58/90/100（识别链接→获取视频信息→拉取播放流→整理清晰度→即将完成）。
- 新增 `GET /api/parse/progress` 返回快照。FastAPI 的同步端点跑在 threadpool，所以请求进行中并发的 GET 能正常响应。
- 前端 `static/app.js`：`pp` 对象（seq/target/shown/raf/timer），rAF 缓动追赶 `min(target+12, 95)`，轮询 180ms。`ppBegin/ppFinish/ppHide` 三件套，全部用 `seq` 校验丢弃迟到回调。
- HTML 进度条插在搜索框与 hint 之间，CSS 用玻璃卡片 + 粉色渐变填充 + 流光动画，完成后转绿、失败转红。

### 踩到的坑
1. **竞态**：上一轮结束留下的 `percent:100` 会在新一轮第一次轮询被读到 → 进度瞬间冲满。修法：`if (!data.active) return;`，只认正在解析的快照。
2. **文案早到**：后端 percent=100 时把 stage 写成"解析完成"，前端显示值还在 60%，出现"已完成 60%"。修法：后端 100% 只写"即将完成"，前端等 shown≥99.4 才改成"解析完成"。
3. **布局跳动**：进度条占一行高度。若结果卡同时渲染，会出现"内容先被顶下去、进度条收起后又弹回 44px"。修法：`ppFinish` 收 `after` 回调，**进度条真正 hidden 后**再 renderResult + scrollIntoView（固定延时不可靠，因为缓动收敛耗时是浮动的）。

### 验证
```
初始   hidden=true
120ms   8%   正在连接 B 站
240ms  25%   正在获取视频信息
480ms  97%   正在获取视频信息
600ms 100%   解析完成（绿色）
~1.2s 收起，结果卡出现，hint 顶部回到 184（无位移）
失败：停在 2% 转红 + 提示条给出原因，1.2s 后收起；紧接着重试正常
8s 无响应 → stage 变「网络较慢，正在重试…」
```
